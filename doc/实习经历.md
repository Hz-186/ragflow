# 第二部分：七大架构闪光点

> 评分为内部复盘口径（0–10）；排序按面试叙事主线，分数为技术难度自评，两者不严格挂钩。

## 闪光点 1：多轮状态与上下文控制体系（9.5/10）——Agent 的"记忆系统"

这是最能体现 Agent 架构能力的一块：**让一个无状态的 LLM 调用循环，变成有记忆、可控规模、可跨轮恢复的对话智能体**。

### 五层上下文控制机制（全部是我的工作）

| 层 | 机制 | 关键参数 | 解决的问题 |
|---|---|---|---|
| ① 历史滑动窗口 | 拼提示词只带最近 N 轮 | **13 轮 = 2N−1 = 25 条**，对齐 Python | 对话无限增长撑爆上下文 |
| ② 工具调用 LLM 摘要 | 每轮结束把工具往返压成一句话 | **≤30 词**，一次小 LLM 调用 | 一轮 5 个工具=几十条消息的爆炸 |
| ③ 多轮问题改写 | 把"它支持吗"这类依赖上文的问题改写为自包含问题 | 改写窗口 **3 轮**，失败回退原问题 | 检索/工具拿不到代词指代 |
| ④ 工具结果截断 | 搜索类工具返回统一截断 | **10,000 rune**，12 个搜索类工具（含 GitHub 检索） | 一次工具调用淹没上下文 |
| ⑤ Memory 独立命名空间 | 压缩记忆与逐字历史分离存储 | History 走窗口截断，Memory 不占配额 | 摘要被窗口截掉 / 历史被工具塞爆 |

**机制 ① 的从 0 到 1**：在 #17137 之前，Go Agent 的提示词里**根本没有历史**——只有一条当前 `UserMessage`，第二轮对话模型直接失忆。这个提交补齐了整套窗口机制：窗口参数（默认 13，与 Python `base.py:45` 逐值对齐）、`2N−1` 消息取法（用 `SnapshotPriorHistory` 拿"已排除当前轮"的历史，与 Python"取 2N 条再删当前条"等价且少一步）、末尾同角色消息合并防重复，配套 126 行窗口测试。

**机制 ⑤ 的设计贡献**（#17010）：原始画布移植里，工具摘要是直接塞进 `state.History` 的——会被窗口截断丢掉，还会污染逐字历史。我把摘要改道到独立的 `AppendMemory` 命名空间（`AppendMemory`/`SetMemory`/`SnapshotMemory` 均为该提交引入），实现"压缩记忆不污染对话历史、不被窗口截断丢掉"的分离。这是有 git 证据的架构决策，不是顺手改的。

**机制 ② 的实现**（`agent.go:392 addToolCallMemory`）：ReAct 每轮结束后，用一次小 LLM 调用，提示词约束"输出一句话、最多 30 词、只描述助手做了什么"，摘要写入独立 Memory 命名空间并随会话持久化、跨轮恢复（对齐 Python `llm.py:525 add_memory`）。**边界要说清**：当前代码里 Memory 的写入、持久化、跨轮恢复、跨状态同步都是通的；"把 Memory 拼进下一轮提示词"是明确规划的下一步（见题目 11 追问 3，这是主动交代的演进位，不是被问出来的窟窿）。

**机制 ③ 的实现**（`agent.go:592 optimizeMultiTurnQuestion`）：取最近 3 轮历史 + 当前输入，让 LLM 改写出"不需要上下文也能看懂"的自包含问题，用于检索与工具调用（对齐 Python `full_question`）；历史少于 2 条或改写失败时安全回退原问题。

### 跨轮状态持久化（#17010，28 文件，+2,363 行）

- `AppendCurrentUser` + `activeHistoryIndex`：游标精确标记"当前轮用户输入"，拼提示词时快照排除，避免同一问题在历史里出现两遍；
- `History`（逐字对话）与 `Memory`（压缩摘要）分命名空间，各自独立保留策略；
- `IncrementConversationTurns` 兼容 5 种 JSON 数值类型（int/int32/int64/float32/float64）——历史会话由不同版本与解码路径写入，数值表示并不统一，自增前必须归一；
- 扩展画布状态序列化机制处理 `sync.RWMutex`/`atomic.Bool` 等不可序列化字段——框架的中断恢复要把整个状态存进 Redis，不处理会直接报 "unknown type"；
- `cloneJSONReflect`/`cloneMapSlice`（约 77 行）反射深拷贝：并行分支拿到的快照与原状态彻底脱钩；
- `SetRetrievalReferences`/`GetRetrievalDocAggs`（72 行）：检索引用聚合进状态，供前端引用条渲染。
- 测试：+691 行 e2e（20 个）+ 持久化 3 个 + 状态 11 个 + 深拷贝验证。

**一句话总结**：这一套让 Go Agent 从"一问一答的无状态调用"变成了"有记忆、可控规模、可中断恢复的多轮智能体"。

## 闪光点 2：实时流式输出管线（9/10）——Agent 的"嘴"

**提交集群**：7 个提交合计 +3,786/−896 行——SSE 管线核心（#17791/#17034/#17353）、历史窗口（#17137）、供应商流式响应与用量处理（另 3 个），全部带回归测试（如 #17791 269 行、#17353 125+163 行、#17034 59 行、#17137 126 行窗口测试）。

### thinking 不实时（#17791）——两个根因叠加

1. **工具调用检测只看第一个 chunk**：eino 框架默认只检查流里第一个非空片段，而供应商把 ToolCall 追加在 SSE 流**末尾**——模型先解释再调工具时被误判为"不调工具"。我实现 `scanAllStreamForToolCall`：整轮读到 EOF 再判定（对齐 Python `async_chat_streamly_with_tools`），保持 `tool_choice=auto`。该函数 100% 归我。
2. **采集器启动晚于执行**：流采集器在图主循环里同步消费整轮，旧代码先执行后启动采集器，整轮 delta 被缓冲。我把 `emitAgentModelStreams` 前移到执行之前（它阻塞在框架 onStart 信号上，顺序安全），并在两条错误路径上排空采集器防 goroutine 泄漏。

### "[DONE]" 泄漏到前端（#17034）

传输层哨兵（OpenAI 兼容的流结束标记）混进业务消息流。在统一模型适配层 `EinoChatModel.Stream` 一处拦截，覆盖全部供应商——**协议哨兵必须在进入业务数据之前被拦截**。

### Agent→Message 答案重复（#17353，+923 行）

Agent 实时流式输出 + 下游 Message 节点引用其完整输出再渲染 = 两份答案。我设计的去重协议放在运行时发射器（`runtime/context.go`，我占 65%）：**只有与上游已流式输出内容一字不差才抑制**；Message 做了任何变换则放行。`EmitCanvasMessage` 去重核心逻辑我占 56/66 行。

## 闪光点 4：分布式会话取消（9/10）——Agent 的"急停按钮"

**#17462，37 文件，+1,323/−324**。多实例部署下"用户点停止，停的必须是对的那次运行"：
- 运行时租约结构 `activeAgentRun{leaseToken, cancelRun, cancelRequested atomic.Bool}`；
- 取消原语（`canvas/cancel.go`，共建）：Redis 键 `{sessionID}-cancel`，**500ms 轮询**（注释成文了取消延迟与 Redis 压力的权衡：最坏新增取消延迟 ≤500ms），**24h TTL** 防陈旧标记误杀下一次运行；
- `CancelSessionRun` 三级路径：① 本实例活跃运行直接取消；② 跨实例写标记前用 **Lua 脚本原子校验租约令牌**（防取消别人的运行）；③ 两者皆无则幂等 no-op——持久化会话不是活跃运行的证据，刻意不兜底以免误杀复用同 sessionID 的后续运行；
- 4 条路径 miniredis 集成测试：越权取消被拒、会话隔离、已结束会话不重建标记、初始化失败释放会话。

## 闪光点 5：检索组件与混合权重体系（9/10）——Agent 的"眼睛"

**#17845，17 文件，+1,494/−134**。`NLPRetrievalAdapter`（638 行，我占 52%）把 Agent 工具层桥接到与 Chat/数据集搜索同一套生产检索引擎：

- **权重换算**：画布"关键词权重" → `向量权重 = 1 − keyword_weight`，融合通式 **`sim = kw×词项 + (1−kw)×向量`**，默认 kw=0.7（即词项 0.7 + 向量 0.3）；
- **词项侧字段加权**：`正文×1 + 标题×2 + 关键词×5 + 问题改写×6`；词级相似度 = 单词 0.4 + 二元组 0.6；
- **rerank 预算**：`Top = TopN×4`（默认要 8 条召回 32 条精排）；重排分页 `ceil(64/pageSize)×pageSize`；
- **空结果两级降级**：自动放宽 `min_match 0.3→0.1`、向量阈值 →0.17 重试；
- **五级增强管线**（翻译、TOC 级失败安全回退原查询/原结果；元数据过滤级失败直接报错，不静默放行）：元数据过滤 → 跨语言翻译 → 问题标注 → TOC 目录增强 → 子块扩展（命中子块带出父块）；
- **跨库嵌入兼容性校验**：按基座模型名（如 `BAAI/bge-m3`）分组，同一模型不同供应商实例放行，不同向量空间提前报错；
- **架构手法**：窄接口 `modelResolver`/`retrievalEnhancer` + 独立 `retrievalbridge` 包打破循环依赖；
- 测试：配套回归测试 57 个（检索直接相关 49 个）。

| 取消轮询间隔 | 500ms | 最坏新增取消延迟 ≤500ms 与 Redis 压力的平衡（注释成文） |

| 混合检索权重 | 默认词项 0.7 / 向量 0.3 | 通式 `sim = kw×词项 + (1−kw)×向量`；企业知识库专有名词多，精确命中优先、语义兜底 |
| 相似度阈值 | 0.2 | 常态过滤阈值；注意区分——空结果降级时向量阈值放宽到 **0.17** 重试（两个值角色不同，别说串） |
| 字段加权 | 标题×2 / 关键词×5 / 问题×6 | 让"文档讲什么"压过"正文碰巧提到" |
| 词级相似度 | 单词 0.4 + 二元组 0.6 | 兼顾精确词命中与短语连续性 |
| rerank 预算 | TopN×4 | 粗排多召回给精排留余量（要 8 召 32） |
| 空结果降级 | min_match 0.3→0.1 | 宁松勿空，避免"库里有却查不到" |
| 模型上下文预算 | 97%（LLM 组件） | `fitMessages` 机制，Agent 链路的已知演进方向 |

## 3.3 Agent 质量如何评估（"用测试集吗？"的标准答案）

**直接回答**：仓库里没有对 Agent 答案质量的离线准确率评测集（没有 golden QA 这类标注数据集，即 RAGAS 这类评测框架所需的输入），Agent 的质量靠**四层质量门**保证——这套体系是我们从零移植时建立的：

| 层 | 手段 | 规模 | 保证什么 |
|---|---|---|---|
| 1. 行为 parity 单元测试 | **以 Python 版为行为 oracle**：每个机制找 Python 对应实现逐语义对齐再写测试 | 1,348 个测试函数、550+ 处对齐引用 | 移植不改变行为（如 2N−1 窗口、Python 输出键优先级、`full_question` 语义） |
| 2. E2E 全链路测试 | `agent_run_e2e_test.go`：启动→工具调用→状态持久化→跨轮恢复整条跑通 | 20 个场景、+691 行 | 多轮/持久化等单元测不到的组合行为 |
| 3. 集成测试 | miniredis 模拟 Redis（取消 4 路径）、httptest 模拟供应商 SSE | 取消/流式/用量各成体系 | 分布式与协议边界的真实性 |
| 4. 人工验证 | 大 PR 附 curl 命令 + 前端截图的 Testing 小节 | 20/105 个提交 | 用户可见行为的最后一道关 |

另有团队级负载工具（CLI benchmark：并发×迭代测 QPS/成功率）用于吞吐回归。

**如果被追问"准确率怎么量化、提升了多少"——诚实 + 方法论**：
> "移植期没有现成的答案质量评测集——行为 parity 在移植期就是质量目标本身，所以'提升'体现在两处：一是**从 0 到 1 的行为补齐**——比如历史窗口上线前，Go Agent 第二轮对话 100% 失忆，上线后多轮行为与 Python 版逐用例对齐；二是**回归零复发**——每个修复都带回归测试，同类问题没有二次出现。如果要建准确率评测，我会用三层指标：检索侧用标注问答对测 recall@k 和 MRR；答案侧用 golden QA + LLM-as-judge 打分；再加 Python/Go 双端一致率作为移植特有指标。准确率评测集是我明确列出的下一阶段基建，不是'没做过所以回避'。"

# 第四部分：面试问答（11 题，含追问与口语化原理）

> 回答用"讲给同事听"的口语：先现象 → 再原因 → 最后方案。名词都在解释之后才出现。

## 题目 1：模型的思考过程是怎么实时显示在前端的？出过什么问题？

**口语回答**（按"现象 → 根因 1 → 根因 2 → 方案"讲）：

**现象**：我们后端跑 ReAct 循环——模型想一步、可能调工具、再想一步，每步都往外吐字，前端靠 SSE 要"逐字蹦"的效果。但深度思考模型的思考内容是整轮憋完才一次性出来的。

**根因一（工具检测误判）**：工作流框架默认判断"这轮要不要调工具"只看流里**第一个**非空片段——但 OpenAI 风格协议里工具调用在流**末尾**，模型先解释再调工具就被误判成不调。我改成整轮读完再判断。

**根因二（采集器时序）**：读完一轮是要花时间的，而负责转发给前端的采集器是在执行**之后**才启动的，启动时这轮已经被框架憋在手里了。

**方案**：把采集器挪到执行**之前**启动——它会阻塞等框架的"已开始"信号，所以先启动是安全的——模型一边吐字采集器一边转发，就实时了。错误路径上还要等采集器排空退出，不然 goroutine 泄漏。

**追问 1：为什么采集器先启动是安全的？** 它启动后阻塞等"执行已开始"信号（框架 onStart 回调关闭），顺序是：采集器就位挂起 → 执行开始 → 信号唤醒 → 开始读流。先启动只是保证"一吐字就有人接"。
**追问 2：执行报错了这个提前启动的 goroutine 怎么办？** 每条错误路径都先等它退出再 return；它内部读到流关闭就往带一个缓冲的 done channel 发结果然后结束。缓冲是防它发送时没人接收而卡死。
**追问 3：为什么不改框架默认检测器？** 框架把检测器做成可插拔的就是给这种场景的；我们还要跟 Python 语义对齐（Python 也是读完一整轮再决定），所以自己实现读到 EOF 的版本，既正确又不动框架。

## 题目 2：前端收到一串 "[DONE]" 是怎么回事？

**口语回答**：
OpenAI 风格流式接口最后会发一个 `[DONE]` 标记，意思是"传输结束"——它是运输层的封条，不是货物。我们的驱动解析 SSE 时没挑出它，混进了"模型说的话"一路到前端。修法是在统一模型适配层判断：内容等于 `[DONE]` 直接丢弃。本质是**分层问题：协议哨兵必须在进入业务数据之前拦截**，晚一层就要层层设防。

**追问 1：为什么在适配层过滤而不是各驱动里？** 几十家驱动都走同一个适配层，一处收口全覆盖，驱动里写会漏。
**追问 2：还有哪些类似的"传输层杂质"？** 心跳空片段、混在最后一个片段里的 usage、reasoning 前的多余换行——都在共享响应处理层统一做了跳过、提取、剥离。

## 题目 3：Agent 节点后面接 Message 节点，前端收到两份答案，怎么修？

**口语回答**：
画布里 Agent 节点"边想边说"，实时把字推给前端；但下游 Message 节点的模板又引用 Agent 的完整输出再渲染一遍——两条路都到前端，用户看到两份。
最粗暴的修法是"Message 见上游是 Agent 就不输出"，但会误伤——Message 可能想做二次加工。所以我把去重放在运行时事件发射器：**只有要发的内容和已流式发过的一字不差才抑制**，有任何改动就放行。反方向的 bug（为防重复把增量全吞了）也一起修了——"实时增量"和"终态去重"分开处理。

**追问 1：流式是一片片的，怎么跟完整答案比"一字不差"？** 发射器累积已发送内容，Message 渲染完得到完整字符串后在终点做精确相等比较。
**追问 2：去重放哪一层纠结过吗？** 纠结过。放 Agent 里它不知道下游会不会再渲染，放 Message 里它不知道上游流式过没有；只有运行时层同时握有"已发了什么"和"要发什么"，所有权归它。

## 题目 4：多实例部署，用户点"停止"，怎么保证停的是对的那次运行？

**口语回答**：
单实例好办：内存通道直接关。多实例麻烦：请求在 A 实例，取消可能落在 B 实例，B 内存里没有这次运行。
我们分三步。第一，运行开始时在 Redis 用会话 ID 登记**租约令牌**，谁在跑有据可查。第二，取消进来先看本实例有没有这个会话的运行——有就直接取消；在别的实例时，写标记前先用一段 **Lua 脚本原子校验**调用方的租约令牌和活跃会话登记的令牌是否一致，一致才允许置位取消标记——值只是占位哨兵，鉴权在写入那一刻完成。第三，在跑的实例每 500 毫秒轮询一次这个键，看到非空就停——写入时已鉴权，运行侧不用重查。
两个细节：500 毫秒是"取消响应延迟"和"Redis 压力"的平衡，注释写了权衡；键设 24 小时过期，不然这次结束后标记还在，下次运行一进来就被旧标记取消。

**追问 1：为什么校验租约令牌？** 没有它，知道会话 ID 就能取消**别人**的运行。令牌是运行时生成的随机值，核对通过才允许写标记——"取消也要鉴权"。我们专门测了越权路径：拒绝且不生效。
**追问 2：500ms 轮询是不是很土？为什么不用 pub/sub？** 轮询最坏多 500ms 延迟，但无状态、掉线免处理、五行代码。pub/sub 要维护订阅、处理重连丢消息和"标记先于订阅"的竞态。对低频、能容忍半秒延迟的取消，轮询更稳。
**追问 3：运行刚结束取消才到，会不会埋雷？** 测过：已结束会话不创建标记，加上 24h TTL 双保险。第三级路径（既无活跃运行也无租约）刻意做成幂等 no-op——持久化的会话不是活跃证据，写标记反而可能误杀复用同会话 ID 的后续运行。

## 题目 5：第二轮提问时 Agent 失忆、或把问题重复带进提示词，为什么？

**口语回答**：
两个容易错的地方。
第一，"当前问题"和"历史"的边界。用户问第二个问题时，我们先把问题追加进历史（状态要完整），但拼提示词时直接全塞进去，当前问题就出现两次：历史末尾一次、"当前输入"位置一次。所以我给历史加了游标标记"当前轮从哪条开始"，拼提示词时用快照把这部分摘出去，模型看到的是干净历史 + 当前问题。
第二，状态要能存能取。画布状态里有互斥锁、原子布尔这种天生不能序列化的东西，而框架的中断恢复恰恰要把整个状态存 Redis。序列化的骨架在画布移植时建立，我做多轮持久化时扩展它：序列化时剥掉这些字段、反序列化时重建——不处理恢复路径直接报"未知类型"。
还有个小坑：会话轮数从 JSON 读出来可能是五种数值类型（int、int32、int64、float32、float64）——历史会话由不同版本和解码路径写入，数值表示并不统一——自增前必须统一归一，否则某些轮次后类型断言会挂。

**追问 1：历史和记忆为什么分开存？** 历史是逐字记录，无限增长只能截窗口；记忆是压缩摘要，要一直带着。混在一起，截历史会把摘要截没，不截又撑爆上下文。分开命名空间，保留策略各自独立。
**追问 2：快照为什么要深拷贝？** 并行分支同时读状态，快照如果只是引用，一个分支改了状态另一个的"快照"跟着变。我用反射深拷贝让快照与原状态彻底脱钩。

## 题目 6：关键词搜不到同义词、向量搜不到型号，怎么解决？权重怎么定？

**口语回答**：
混合检索解决的标准矛盾。纯向量懂语义——"怎么退货"能匹配"退换货流程"——但对精确字符串不敏感，搜型号错误码会召回一堆相近但不对的。纯关键词相反：型号一搜一个准，换个说法就没了。
我们两路都查再加权融合：`综合分 = 0.7×词项 + 0.3×向量`。关键词是大头，因为企业知识库场景用户常搜专有名词、编号、人名，必须精确命中；语义是兜底。画布上用户调"关键词权重"，我们内部做 `向量权重 = 1 − 关键词权重` 换算。
词项那路也不是数词频：标题算 2 倍、抽取关键词 5 倍、问题改写 6 倍——让"文档讲什么"压过"正文碰巧提到"。还有保险：查空了自动放宽条件重试（最小匹配度 0.3 降到 0.1），避免"库里有却空手而归"。

**追问 1：召回数和返回数什么关系？** 用户要 8 条，我们召回 32 条（TopN×4）给重排模型精排——粗排分数糙，相关文档可能排第 15，池子大精排质量才好。4 倍是成本和质量的平衡。
**追问 2：多个知识库一起查有什么问题？** 嵌入模型不一致是最大的坑：两个库向量空间不同，相似度分数没意义。我按**基座模型名**归一化校验——同模型不同供应商实例放行，不同模型提前报错。
**追问 3：检索为空前端看到什么？** 修过：画布可配置空回复话术，之前空结果直接抛错话术不生效；现在走正常返回路径。

## 题目 7：手动加一个 chunk 的完整链路？哪里有并发问题？

**口语回答**：
这是我在 RAG 方向最完整的链路。一个手动 chunk 进来：先做数据集/文档双重权限；校验内容非空和 `tag_feas`（自定义标签特征）格式；生成 chunk ID——内容加文档 ID 做 xxhash，重复提交同 ID，天然幂等；双路分词（常规 + 细粒度）供不同检索字段；调该库的嵌入模型生成向量写进文档引擎（租户级索引）；事务里更新 chunk 和 token 计数。
并发问题在图片合并：同一张图被多个 chunk 引用时不重复存、合并引用。两个请求同时给同一 chunk 传图会撞车——都读到"还没存"然后各存一份互相覆盖。我按 chunk 维度做了引用计数锁表：同 chunk 排队、不同 chunk 不互斥、没人用就回收。

**追问 1：删块为什么不减 token 数？** 删除时拿不到该块当时的 token 数，按现在的分词器重算还可能因版本变化算出不同的数。宁可保守不减，不能减出负数错账——取舍写在提交说明里。
**追问 2：ID 用内容哈希，改一个字 ID 就变？** 手动块场景编辑就是删旧建新，哈希换来的幂等和防重复提交更值钱。

## 题目 8：字段明明存了，为什么搜不到？

**口语回答**：
修过技能搜索：按名字搜一条没有。查 ES mapping 发现 `name`/`tags`/`content` 是**只存不索引**的展示字段，没建倒排索引，查它们永远空；能搜的是 `name_tks` 这类分词字段。改查询指向分词字段就好了。本质：搜索引擎里"能显示"和"能搜索"是两件事——存不存、索引不索引、怎么分词，是 mapping 里三个独立决定。

**追问：字段加权（标题×2）在引擎侧怎么实现？** 不在 ES 里做加权查询，而是把各字段分词结果按权重拼成"虚拟文档"再匹配——展示与检索字段分开，检索字段内部按权重组合。

## 题目 9：供应商 token 用量为什么总对不上？怎么保证计费准确？

**口语回答**：
原因五花八门：有的流式最后一片才带 usage，有的不发；有的放 `usage`，有的放 `meta.tokens`，有的把思考 token 单拆；更常见是上层没接 usage 回调，数据静默丢。
我做三层。第一层，所有供应商共用的记账流水线：流式非流式都过同一处理函数，内容、推理内容、用量分开提取。第二层，兜底：上层没传接收器也会生成最小占位记录上报——宁粗勿丢，保证计费管线不漏请求。第三层，各驱动按协议填统一结构并打类型标签（chat/embedding/rerank），因为计费单价不同。
防御细节：时间字段零值（没被赋值）拿去算耗时会产生大得离谱的脏数据（注释原话"50 年量级 epoch 差"），加了零值判断跳过。

**追问 1：流式和最终 usage 会重复记吗？** 不会。流式 usage 是累计值只认最后一个非空的；非流式一次性读取；两条路径不同时发生。
**追问 2：怎么防一个请求打爆供应商限额？** 双层：服务层用模型元数据校验维度和批量上限，超了**不发真实请求**；驱动层纵深防御，超批量内部分批。元数据缺失显式报错不放行。

## 题目 10：画布/工作流引擎是你写的吗？

**口语回答**（共建分工版）：
画布/工作流引擎是我和另一位核心架构师**两个人共建**的，分工很清晰：他主导 DSL 到 DAG 的编译框架和中断恢复基建——把画布定义编译成执行图、处理"等用户输入"这类中断；我主导运行时执行层——一次运行怎么被编排起来（RunAgent）、模型输出怎么流式到前端、运行怎么取消、多轮状态怎么持久化、上下文怎么控制、工具和检索怎么接进来。调度器里的状态注入、节点事件发射、取消原语是我们持续共同演进的部分。
打个比方：编译框架是把图纸变成流水线，我做的是让流水线真正运转的部分——操作台、急停按钮、交接班记录。整个 Go Agent 就是我们俩这样配合搭起来的。

## 题目 11：多轮越聊越长，上下文超窗口怎么办？

**口语回答**：
先说结论：Agent 链路**没有 token 计数式硬预算**，靠五层机制把上下文增长控制成线性的——这五层都是我的工作。
第一层**历史滑动窗口**：只带最近 13 轮（25 条消息）。这个机制是我从 0 到 1 加的——之前 Go Agent 提示词里根本没历史，第二轮直接失忆。按"轮"截断不会把对话拦腰切断。
第二层**工具调用摘要**：每轮结束用一次小 LLM 调用把本轮工具往返压成一句不超过 30 词的摘要——模型不需要重读几十条工具原文，只需要知道"查过什么、结论是什么"。
第三层**多轮问题改写**：用户说"它支持吗"，先让 LLM 结合最近 3 轮改写成自包含问题再去检索——不然检索引擎拿到代词什么都查不到。改写失败安全回退原问题。
第四层**工具结果截断**：12 个搜索类工具统一 10,000 字符上限（rune，Unicode 码点，中文按 1 计），防一次工具调用淹没上下文。
第五层**Memory 独立命名空间**：这是我刻意做的架构决策——原始实现把工具摘要直接塞对话历史，会被窗口截掉还污染历史；我建了独立 Memory 存储，压缩记忆不占窗口配额、不随历史截断丢失。
要说边界也坦白两点。一是按轮截断不如按 token 精确——代码库里 LLM 组件有一套按模型上下文 97% 做消息裁剪的预算机制（`fitMessages`），Agent 目前没复用，接上它是自然演进方向。二是 Memory 只增不减：每轮最多加 30 词，是线性可控的，但超长会话的 Memory 淘汰策略还没做，这是我列出的演进点——主动说，不等被问。

**追问 1：窗口为什么是 2N−1 这个怪数字？** 一轮对话是"用户 + 助手"两条，N 轮是 2N 条；但最新那条用户消息就是当前问题，会单独拼进去，窗口再带就重复了。Python 是取 2N 条再删掉它；我的历史快照天生排除当前轮，直接取 2N−1，效果等价还少一步。
**追问 2：为什么不上 token 计数？** 想过。窗口制截断永远落在"轮"边界，不留半句话；token 截要每轮全量过分词器，截断点还可能落在消息中间产生畸形上下文。窗口 + 摘要 + 截断已经把每轮新增控制成常数了。真要精确控制，现成的 `fitMessages` 机制可以接，不用从零造。
**追问 3：Memory 下一轮模型真的能看到吗？** 这里要诚实分层，不能含糊。当前实现里，Memory 的**写入、持久化、跨轮恢复、跨状态同步**全链路都是通的——会话重启、跨实例恢复后摘要都还在，而且它和逐字历史隔离，不会被窗口截断丢掉。但"把 Memory 拼进下一轮提示词"这一步当前还没接上——拼提示词的函数只读历史窗口，这是我明确规划的下一步，因为底座（独立命名空间 + 持久化）正是为注入准备的。面试时我主动把这个边界讲出来：底座已就位、注入一步之遥——主动交代的演进位不是窟窿，被问出来才说是窟窿。
